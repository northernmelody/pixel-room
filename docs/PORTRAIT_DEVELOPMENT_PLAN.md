# Pixel Room 竖版独立入口：开发阶段与子智能体任务规划

> 日期：2026-09-11；参考源码基线：`7a78c0f`。
> 本文保留最初的阶段规划。用户随后授权开发，现已完成 S0–S3 与 S4.1 第一条生活闭环；具体实现、验证与尚未完成的范围见 [竖版交付记录](../portrait/README.md)。
> 横版现状依据：[当前开发说明](DEVELOPMENT.md)。下文 S4–S6 与多角色分工仍为后续计划；S0–S2 实际采用主智能体 + 1 个 Sol/high 绘制子智能体，S3 由主智能体集中完成。

## 1. 目标、边界与推荐决策

目标是在现有项目中新增一个独立的竖版 Pixel Room，以参考图的三层住宅剖面组织空间，保留现有人物、猫狗、家具、物品、剧情和生活行为。

确定边界：

- 原横版入口 `/`、`index.html`、`js/`、`css/`、`assets/` 保持原样；不加移动端重定向，不替换首页，不在旧页面挂入新脚本。
- 新入口拟为 `/portrait/`，实际文件 `portrait/index.html`。可直接访问；后续首个版本不必修改原首页增加导航。
- 竖版运行逻辑、样式、布局和测试独立。初期使用独立存档键 `pixel-room-portrait-save-v1`，不读写、迁移或重置横版存档。
- 保留现有像素角色与物件身份、数量、主要配色及功能；允许改变位置、房间分配和布局留白。不要照着参考图替换现有家具或宠物造型。
- 可新增房屋外壳、屋顶、楼板、楼梯和必要平台；庭院只做少量场景收边，不能挤占室内可用空间。参考图中的其他物件不自动进入需求。
- 原来的四间房与四扇窗、六盏灯都应有去向。MOMO 继续通过文字与通话呈现；户外门继续作为未开放门区。
- 开发范围包含现有核心生活能力的迁移；第一个可展示里程碑只要求静态场景，不能把静态版本称为竖版改造完成。
- 部署、替换生产首页、横竖版自动切换、合并存档、户外玩法和新增任务奖励体系均不在本计划首版范围。

推荐总体安排：先完成“保全元素的静态竖版”，再验证“连续上下楼的一个人物”，最后迁移生活和宠物系统。架构围绕显式楼层、家具锚点和行走路径建立。

## 2. 布局方案与尺寸验证

### 2.1 三层分布

| 层级 | 室内分区 | 保留内容 | 连接 |
| --- | --- | --- | --- |
| 顶层 | 卧室为主 | 床、枕头、被子、衣柜、7 个玩偶/抱枕、卧室窗、床头柜灯、顶灯、吉他、时钟、季节物件 | 右侧楼梯平台；衣柜和窗帘仍可供猫活动 |
| 中层 | 左工作区、右卫生间 | 全套电脑桌椅、书架与两封信、长颈鹿相框、工作区窗/灯/季节设备；洗手台、镜子、马桶、毛巾、淋浴、卫生间窗/顶灯 | 卫生间保留独立门口，动线不能穿过马桶和淋浴设施 |
| 底层 | 厨房、右侧门区 | 冰箱、吊柜、灶台、水槽、餐桌凳、厨房窗/顶灯、装饰、快递、5 类收藏的对应位置、狗窝、猫狗粮碗、户外门 | 楼梯落地接公共通道，宠物窝/碗不堵楼梯口 |

收藏仍在原语义房间展示：雕像在工作区书架、彩杯在厨房、画在卧室、小盆栽在桌面、花瓶在卫生间。参考图的猫爬架可以作为后续结构补充，先保留原有五个攀爬点，不额外扩张宠物玩法。

### 2.2 修正上一轮尺寸建议

`180×320` 只能视为方向草案，不能直接定稿。现有工作区宽 92、卫生间宽 68，二者已占 160 逻辑像素，180 宽画布很难再容纳楼梯、分隔墙和边框。

本计划以 **216×384（9:16）为候选布局尺寸**，4 倍内部画布为 864×1536。一个可供试排的横向预算：外墙 8 + 中层房间 164（92+4+68）+ 通道分隔 4 + 楼梯带 32 + 外墙 8 = 216。

这只是宽度可行性测算，不是最终房间坐标。S0 必须用全部家具真实边界和最大动作轮廓验证：人物俯卧撑、持吉他行走、狗的身体、开门范围、猫跳跃弧线均要容得下。若中层仍不够，优先调整整体尺寸或房间排列，不能压扁家具和角色。

纵向按三层接近原可用墙高来试排；屋顶、天空和底部庭院高度最后分配。首版不为了接近参考图而强行增加大量空景。

### 2.3 布局验收规则

- 每个现有对象在元素映射表中都有唯一 ID、原位置、目标房间、锚点、绘制边界、交互边界和功能去向。
- 普通家具/实体保持原像素尺度；全画面适配屏幕时统一缩放，禁止对单个对象非等比拉伸。
- 四间房通过实际可走的门口、平台和楼梯连通；人物不能靠穿越卫生间设备到达工作区。
- 375×812、390×844、430×932 竖屏能一屏看清主要室内；320×568 列为最小适配用例。最终尺寸应以这些视口验收，而不是仅看原始 Canvas。
- 设置、时间、通话卡片与歌词有保留区；信件等小物可扩大透明热点，必要时用生活物件列表辅助选择，不改家具本身造型。

## 3. 独立实现结构与复用策略

### 3.1 计划目录

```text
portrait/
  index.html                  独立入口
  style.css                   竖版专用样式
  js/
    main.js                   初始化、装配与主循环
    config.js                 竖版配置、视口与时序默认值
    contracts.js              模块共享数据契约
    content/                  菜谱、对白、信、歌曲的固定快照及来源记录
    layout/                   楼层、房间、物件清单、锚点和热点
    scene/                    家具/角色像素绘制、外壳、缓存和合成
    navigation/               平台、楼梯路径、移动与重定向
    actors/                   主角活动、猫、狗各自状态机
    ui/                       物件交互、电脑、信件、通话、歌词和设置
    systems/                  时间、天气、声音、灯光、存档与动态物品
  tests/                      新版单元/流程/浏览器用例
  artifacts/                  开发基线、截图和验收报告
docs/
  PORTRAIT_DEVELOPMENT_PLAN.md 本文
```

文件可在契约阶段合并，避免为了模块数量过度拆分。核心约束是目录与写入责任清楚，不要求每个小函数一个文件。

### 3.2 推荐复用方式

原项目使用全局 `window.PixelRoom`、固定地板和封闭在函数作用域内的绘制函数。仅加载旧 `character.js` 后增加 y 偏移，不能正确解决跨层目标、跟随、命中和前后遮挡。

因此建议：竖版使用原生浏览器模块建立独立运行时；复制或提取必要的内容数据和绘制实现到新目录，改为接收局部坐标与明确状态。原文件只读。纯静态聊天背景可引用现有 `assets/chat-bg.jpg`。

复用分层：

| 类型 | 方式 | 验收 |
| --- | --- | --- |
| 对白、信、菜谱、零食、歌曲 | 从既有数据建立竖版固定快照 | 100/2/38/6/3 条目与正文、ID一致；记录来源基线 |
| 家具、人物、猫狗像素绘制 | 提取到新目录，转换为局部锚点与状态参数 | 同姿势与物件对比，保留原造型，不重新设计一套 |
| 时间、天气、音频等 | 移植可独立逻辑，消除旧全局依赖 | 行为等价、初始化一次、无旧存档副作用 |
| 旧主循环、位置状态、渲染器、点击分派 | 新目录独立实现 | 只操作竖版世界与 UI |

代价是短期存在两份部分逻辑。以来源记录、元素映射和功能对应测试控制差异；竖版稳定前不修改旧模块抽公共层，稳定后的去重是另一个任务。

### 3.3 必须先定下的契约

以下是概念字段，不是本轮编写的代码：

| 契约 | 建议字段/操作 | 解决的问题 |
| --- | --- | --- |
| 楼层与房间 | floorId、roomId、bounds、platformY、doorAnchorIds | 不再用 x 区间推断人物所在楼层 |
| 家具 | itemId、roomId、origin、drawBounds、hitBounds、supportAnchors | 绘制、点击、宠物支撑面来自同一个位置源 |
| 行为锚点 | anchorId、worldX/worldY、approach、facing、supportId | 区分冰箱本体与取物站位、床边与睡眠位 |
| 实体位置 | entityId、worldX/worldY、floorId、surfaceId、pose、facing | 人物、宠物和点击共享真实显示位置 |
| 移动请求 | moveTo(entityId, anchorId)、cancel/replan、arrival | 活动只能在到达后开始，路径取消不会重复完成 |
| 行为会话 | actionId、phase、targetAnchorId、heldItem、cancelReason、resumePolicy | 通话和吉他等打断有明确收尾 |
| 时钟与随机源 | 北京日期时间、动画 dt、可注入测试时钟/随机源 | 日期、活动计时、测试加速不混用 |
| 环境/存档 | 只针对 portrait 的状态与命名空间 | 并排打开横竖版不会相互修改灯光与进度 |

主智能体在 S0 冻结契约与负责人。后续需要修改时先提出受影响调用方和迁移方案，由主智能体统一更新，避免并行任务各自定义一套坐标。

## 4. 上下楼的首版要求

采用预设的楼梯折线路径和平台连接，无需开发通用物理引擎。移动顺序为当前锚点 → 本层楼梯口 → 逐段楼梯/平台 → 目标层出口 → 目标锚点。

- 实体的世界坐标随路径连续变化，不通过“入口消失、出口出现”代替完整跨层移动。
- 姿势可先复用原行走动作，增加沿楼梯斜向位移；脚底贴合台阶，不能浮空或穿过楼板。
- 楼梯栏杆可局部遮挡实体，但不能把隐藏后的瞬移当作已验收连续路径。
- 暂停、改目标和通话抢占从当前位置重算后续路径；只有有效完成到达请求，活动才进入坐下、吃饭或睡眠阶段。
- 狗跟随使用人物路径或落后路点，不能对另一层人物只追 x 坐标。猫先从高处落地，再走到楼梯，跨层后再攀爬家具。
- 绘制按房间后景、角色所在表面、家具前缘/楼梯栏杆分层；不能继续沿用“人物→猫→狗”的全局固定顺序处理所有遮挡。

### S0：基线与规划定稿

- 记录开工时实际 Git 基线、现有未提交修改与文件哈希，保留用户改动。
- 从原代码核实全部元素及动作，不只参考旧文档；建立逐项对应表。
- 使用只读检查和测试记录旧版现存问题；已知 2026-09-10 的 7 项冒烟中 4 通过、3 失败，不能称为当前重新运行结果。
- 布局设计包括站位、开柜/开冰箱空间、全部楼梯入口和卫生间到工作区的通路。
- 为纯内容、像素绘制及行为迁移写清来源与负责人。

### S1–S2：独立入口与静态场景

- 先由 A0 建立最小运行时与模块边界；新页面不加载旧 `main.js` 等自启动脚本。
- 复用像素绘制时以家具局部坐标为单位迁移，禁止截取整张房间图片后让角色在背景上假交互。
- 提供人物、猫狗固定姿态用于比例和遮挡检查；此阶段自动活动可以暂缺，并在验收报告标明。
- 验收原有 7 个玩偶/抱枕、两封信、4 扇窗、6 盏灯以及各季节物件；同一季节不必同时显示夏冬设备，但都应有渲染去向。

### S3：先把移动基础做实

- 定义床、衣柜、吉他、电脑、窗边、健身、逗猫、马桶、洗手台、淋浴、冰箱、灶台、餐桌、狗窝和粮碗的锚点。
- 验证四房间所有 12 条有向往返组合，楼梯中途改目标、暂停恢复、跨两层路线。
- 开发用导航演示入口独立于正常界面，不让测试按钮进入正式生活体验。
- 交付可直接被 A4/A5 使用的移动接口后，再启动完整角色迁移。

### S4：生活与宠物迁移

执行状态：S4.1 已把床、冰箱、灶台和餐桌四个既有锚点串成可完成、可中断、可记录的用餐闭环，并加入取食材、做饭和吃饭画面。完整作息、其余动作、猫狗、通话和任务系统仍待迁移；未完成的流程不会在刷新后续跑。

- 主角覆盖晨间洗漱、三餐、工作/喝水、8 类休闲、通话、淋浴、睡眠、起夜、点击反应及吉他八阶段。
- 电脑保留现有模式规则；通话保留 100 天循环，信件保留正文，歌曲保留歌词与时序。
- 猫保留地面、高处、床下、逗猫和连续触摸反馈；狗保留 9 状态，增加跨层路径跟随。
- 旧版已经识别的状态残留不应原样迁移：例如零食吃完清食物、柜门/冰箱门随取消收尾。修复限定在新目录，并在对应表注明与旧行为的差异。
- 绝对作息与实体到达应分别处理：21:30 发起通话切换，人物在路上时可显示接通/返回状态，不能为了准点坐床而瞬移。对话句子仍按真实北京时刻选择，不因行走累积漂移。

### S5：环境与持久化

- 四窗按新空间裁剪窗内天空和天气，六灯按新房间边界照明；楼板遮挡不能漏成整栋泛光。
- 新版单独保存衣服、冷却、通话起始日、摸猫统计、灯光、设置和动态物品；重置仅影响新版。
- 只初始化一套音频与天气刷新逻辑；保留默认静音和天气失败兜底。
- 测试时钟可以推进日期，用于通话第 100/101 天、午夜、快递及灯覆盖验证；正常入口默认真实北京时钟。

## 6. 模型、推理强度与任务负责人

### 6.1 分配依据

下表是针对本项目的推荐分工，不是模型已运行或已配置的记录。模型 ID 使用本会话工具列出的可选项，并与官方说明核对。

能力、推理强度和任务范围分别指定：模型决定基础能力，`high/xhigh` 等为推理强度，允许修改的文件和验收要求决定责任。不能把更高推理强度当作自动通过验收。

官方文档将 Sol 对应到 5.6 的旗舰能力，Terra 用于能力与成本平衡，Luna 用于范围明确的高吞吐工作；本文把复杂行为交给 Sol、清单与界面交给 Terra。具体任务分工是项目判断，并未做本项目模型速度或成本实测。[GPT-5.6 模型说明](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)

官方子智能体说明支持单独指定模型和推理强度，未指定时可能继承父智能体；high 适合逻辑追踪和边界检查，更高档应留给困难任务。未来派发时显式带上本文指定项，避免所有任务沿用主智能体的高强度配置。[子智能体配置说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)

Astra 放在架构、跨层导航和最终审查是基于这些任务的跨模块约束较多，结合其复杂长任务定位作出的推荐。默认不使用 max/ultra；遇到有证据的复杂卡点再升级单个任务。[GPT-6 Astra 说明](https://developers.openai.com/api/docs/guides/latest-model)

## 8. 可派发任务卡

每张卡应同时附带：本文、S0 冻结契约、元素映射表、当前阶段目标、允许写入路径、上游接口及本批次已知问题。全部是未来开发提示，当前不执行。

### A1：元素、内容与功能对应

**模型：gpt-5.6-terra；强度：high。**

只读核对旧源码和开发文档。列出所有默认/季节/动态物件、角色动作、交互、内容数据及存档字段，建立唯一 ID 对应表；注明保留代码但未显示的对象。将需要的纯内容快照放入自己的目录，记录来源提交/哈希。不要改旧文件或业务逻辑。

交付：映射表、纯内容快照、缺项清单、旧版已知缺陷与本次迁移项的区分。验收：没有无去向元素；100 组通话、2 封信、38 餐食、6 零食、3 首歌数量与正文一致。

### A2：场景布局与像素绘制

**模型：gpt-5.6-sol；强度：high。**

先验证三层布局能容纳现有全量物件和动作轮廓，输出候选尺寸与锚点。按已冻结布局提取原像素绘制到新模块；加入房屋外壳、平台、楼梯及明确前后景。禁止用单张背景图替代动态家具，禁止删物件换取空间。

交付：布局数据、家具/角色绘制、热点与支撑面、指定视口截图。验收：元素可辨识，四窗六灯有位置，开门/持物/俯卧撑不穿墙，静态比例及像素风格保持一致。

### A3：跨层路径与移动

**模型：gpt-6-astra；强度：xhigh。**

基于 layout 锚点建立楼梯与平台路径，提供统一移动、到达、取消和重定向接口。将实体位置作为真实世界坐标维护，保证行走、上下楼和持物移动连续；不接管作息或宠物随机行为。

交付：navigation 实现、四房间路线演示、取消/到达事件语义。验收：12 条有向路线可达；楼梯中途换目标不会跳坐标；不穿楼板/洁具；可以让宠物跟随同一路径。

### A4：主角生活与活动仲裁

**模型：gpt-5.6-sol；强度：xhigh。**

迁移既有作息、三餐、洗漱、休闲、通话、睡眠、夜间活动与吉他；所有活动位置从锚点获取，移动交给 navigation。明确每项取消、道具释放、返回与恢复策略。21:30 优先级保持，路途中进入通话不得瞬移到床上。

交付：主角状态机、姿态输出、道具状态、行为接口与关键场景证据。验收：各流程能结束/切换；持吉他跨层、换衣/零食中被打断、午夜起夜可复现；没有重复人或道具悬留。

### A5：猫狗与跨层联动

**模型：gpt-5.6-sol；强度：high。**

保留橘猫和棕色腊肠狗及原状态；用家具支撑面处理攀爬与跳下，用 navigation 处理跨层。狗跨层跟随有自己的路径进度；猫在高处或床下收到交互时先正确离开支撑面。概率规则不自行改成新的养成玩法。

交付：猫狗状态机、交互 API、位置/姿态输出。验收：猫五个攀爬点可达、连续摸猫四阶段正确、狗九状态可触发、跟随不隔楼层瞬移、宠粮递减及刷新正常。

### A6：界面、点击与移动端

**模型：gpt-5.6-terra；强度：high。**

实现独立 UI、统一坐标换算、灯/电脑/人物/猫狗/物件点击，保留信件、通话、歌词、设置与电脑模式。热点使用世界坐标和楼层，避免上下两层同 x 对象误命中。按需加载电脑聊天背景，处理弹窗关闭与焦点。

交付：UI 模块、触屏布局、真实点按证据。验收：手机无需精确点中两像素书脊；弹窗可关可读；不同楼层点击无串扰；调节及重置不影响旧页存档。

### A7：环境、时间与存档

**模型：gpt-5.6-sol；强度：high。**

迁移北京时间、天气、光照、音效、动态物品和跨日逻辑到独立系统。四房间照明受边界/楼板约束；六灯与 UI 共用有效状态。只访问 portrait 存档键，确保声音只初始化一次并默认关闭。

交付：systems 模块、固定天气/时钟测试接口、隔离和跨日记录。验收：刷新与断网可恢复、快递/收藏/补粮推进正确、今日摸猫跨日清零、两个入口并开互不影响存档。

### A8：独立验收与差异审查

**模型：gpt-6-astra；强度：high。**

根据用户目标审查新入口，先建立旧版已知失败记录，再分别测试竖版新增行为和保留功能。必须执行实际浏览器点按、上下楼观察及多视口检查，不能只运行构建或 draw 无异常。只编辑测试和报告；实现缺陷交给对应负责人。

交付：可复现步骤、预期/实际、截图或状态轨迹、缺陷等级、验收结论。验收：每项结论有证据，区分通过/失败/未测，旧版原文件哈希及存档隔离检查完整。
